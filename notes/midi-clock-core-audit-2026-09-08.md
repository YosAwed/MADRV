# MIDI変換時計とOPMコア時計の独立調査

対象は内蔵SoundFont向け同期対策。出力フレーム基準の予約修正とは別に、MIDI変換器の時間計算にも小さな速度差があることを確認した。抽出専用の仮想時計を125 kHzにするとTimer-Bの刻みが整数になり、PRIN_GSの10分の描画比較では累積差が解消した。OPMの48 kHz描画や出力音声のレートは変更しない。**個別の計測結果を、あらゆる曲・環境で音ズレがなくなる保証とはしない。**

## 方法

ローカルの配布用WASMをNodeから直接実行した。ブラウザー、画面更新、SoundFont、音声デバイス、待ち時間は介在しない。

- 変換器: `client/public/manus-storage/madrv-converter-v4_f7f66741.wasm`
- OPMコア: `client/public/manus-storage/madrv-mdx-player-v12_2d6b7625.wasm`
- MIDI変換器: `client/public/manus-storage/madrv-midi-events-v4_2facde2d.wasm`
- 曲: `/Users/awed/Downloads/song.mdr` + `sample.pdx`、`/Users/awed/Downloads/mdr/MEGALITH.MDR` + `MEGALITH.PDX`、同じフォルダーの `PRIN_GS.MDR` と `BOMB.MDR`

OPMコアは48,000 Hzで初期化し、MDR変換・読込・時間計測後に再生開始。`_mdx_player_render` に渡したフレーム数を整数加算し、`_mdx_player_get_play_at_ms` と比較した。PRINの詳細比較は128フレームごとに `_mdx_player_get_hardware_track_note_raw(0)` の変化を記録した。

## 1. 生のMXDRV再生位置は段階的だが、出力サンプルに対する大きな累積速度差はない

2,048フレーム単位、最大180秒の描画での「MXDRV再生位置 − 描画サンプル時間」は次の範囲だった。初期化直後の通常開始の値で、時計の初期差を補正していない。

| 曲 | 差の最小〜最大 |
|---|---:|
| song.mdr（OPM終了まで） | −15.0〜−3.0 ms |
| MEGALITH | −14.7〜−5.0 ms |
| PRIN_GS | −14.7〜−1.0 ms |
| BOMB | −14.7〜+4.3 ms |

Lループを跨いでも再生位置は単調に進んだ。生のカウンター値をタイマーコールバックの到着時刻に対応付けるより、実際の出力フレーム数と各ブロックの再生予定時刻を対応付ける方が、段差に依存しない。

song.mdrは描画時間16.3413秒でOPM終了が検出され、その時の生カウンターは16.363秒だった。旧48 kHz抽出で最後のMIDIイベントは26.3225秒。OPM終了をMIDI全体の終了とみなさず、最終出力ブロックからMIDI末尾の時計を継続する必要性も確認できる。

## 2. PRIN_GSは変換イベント自体がOPMより徐々に先行する

`PRIN_GS.MML` のOPMトラックAとMIDIトラックaには同じ旋律が記述されている。コアの表示用音階値とMIDIの音階には1オクターブの差があるため、**照合時だけOPM側のノート番号へ12を加算**した。再生データや時刻を変えたわけではない。

48 kHz、128フレーム（2.667 ms）単位で600秒の無限再生を描画し、変換器のMIDIトラック16のノートオンと順番に照合した。MIDI側は修正前の実装と同じく、変換ループ窓55.95〜111.642秒を使って以後の周期を55.692秒ずつ延長した。

- 照合した3,616ノートすべての音階順が一致。不一致0件。
- 最初の「OPM状態遷移 − MIDIイベント時刻」は15〜17 ms程度。
- 最後の599秒付近では513〜516 ms。
- 1分ごとの平均差は約40.5、90.4、140.4、190.3、240.3、290.3、340.2、390.2、440.1、489.9 ms。およそ**50 ms/分でMIDIが先行**する。

この方向はユーザー申告の「MIDIが遅れる」とは逆であり、その申告の原因を再現したとはいえない。ただし、修正前の変換時刻にブラウザーの予約遅れとは独立した時計速度差がある証拠になる。音色のアタックや実際のSoundFont波形を測ったものではない。

## 3. MIDI変換器でのtick端数切捨てを示唆する結果

PRINのTimer-B値202では、1 tickの公称時間は `(256 − 202) × 256 µs = 13.824 ms`。48 kHz換算では663.552サンプルになる。変換器の最初の連続ノート間隔は0.16575秒で、`12 × 663 / 48000` と一致する。

変換器へ渡すサンプルレートだけを変えた追加診断では、次の結果になった。

| MIDI抽出レート | 最初の連続ノート間隔 | 変換ループ周期 |
|---|---:|---:|
| 44,100 Hz | 0.165714秒 | 55.680秒 |
| 48,000 Hz | 0.165750秒 | 55.692秒 |
| 96,000 Hz | 0.165875秒 | 55.734秒 |
| 192,000 Hz | 0.165875秒 | 55.734秒 |
| 1,000,000 Hz（直接WASMへ指定） | 0.165750秒 | 55.692秒 |
| 62,500 Hz | 0.165888秒 | 55.738368秒 |
| 125,000 Hz | 0.165888秒 | 55.738368秒 |

OPM側の時間計測は `measure(2) − measure(1) = 18.579秒`、MIDIの旋律1周期に相当する3倍は55.737秒だった。ただし計測値にはms単位の丸めがあるため、それだけを使って正確な倍率を断定しない。

上記は**各tickを整数サンプルへ切り捨て、端数を次のtickへ持ち越していない可能性**と整合する。C/C++の変換器ソースはこのリポジトリ内には見当たらず、内部実装そのものは未確認。1 MHzはJavaScript側の制限を経由せず直接WASMへ指定しても48 kHzと同じ値になり、内部の対応範囲外のようだった。

MEGALITHは48 kHz・192 kHz・1 MHzとも41,489イベントで、最終イベント時刻はそれぞれ311.238750・311.554156・311.238750秒。62.5 kHzと125 kHzでは両方とも311.568384秒、最初の連続ノート間隔は0.113664秒だった。抽出時間はこのMacでPRIN約2.5〜7.3 ms、MEGALITH約8.7〜9.8 msで、高精度化による大きな増加は見られなかった。

## 4. 整数刻みの抽出時計で10分の累積差を解消

192 kHzへ単に上げても公称tickは整数にならない。一方、`125000 × 256 / 1000000 = 32` なので、125 kHzではすべてのTimer-B値について1 tickが `32 × (256 − Timer-B)` の整数になる。62.5 kHzでも16倍の整数だが、今回は125 kHzを抽出専用の仮想時計として採用した。AudioContextやOPMコアを125 kHzで動かす変更ではない。

同じ600秒のOPM描画結果に125 kHz抽出イベントを対応付けると、次の結果になった。

| 比較 | 旧48 kHz抽出 | 125 kHz抽出 |
|---|---:|---:|
| 照合ノート数／音階不一致 | 3,616／0 | 3,616／0 |
| 10分間の時刻差の変動幅 | 500.750 ms | 2.645 ms |
| 回帰傾き | +49.9545 ms/分 | −0.000241 ms/分 |
| 最初の1分の平均差 | 40.548 ms | 15.660 ms |
| 最後の1分の平均差 | 489.877 ms | 15.660 ms |

125 kHzではOPMの状態遷移とMIDIイベントの差が14.336〜16.981 msの範囲を保った。残る変動は128フレームの観測分解能2.667 ms以内。固定の開始差は残っており、実際のSoundFontのアタックを含めた補正とは別問題である。

全4,064イベントの「トラック番号・メッセージ長・メッセージ内容」を順序を保って連結したSHA-256は、48 kHzと125 kHzで同じ `abc21bc2866f84349d662ff4b8c31118913d43aa130f99f1ff0d8d149eb09155` だった。変えたのは時刻計算で、ノート・コントローラー・SysExの内容や順序は変わっていない。

曲全体を一律の倍率で引き伸ばすのではなく、変換器が各tickを整数として扱える時計を指定するため、テンポ変更ごとに異なる端数を個別に回避できる。OPMとMIDIで終了長が異なる曲や、複数OPMループに跨るMIDI編曲を、長さの比だけで強制的に揃える処理ではない。

再現用の独立スクリプト:

```sh
MDR_CLOCK_SOURCE='/Users/awed/Downloads/mdr/PRIN_GS.MDR' node scripts/verify-mdr-timing-clock.mjs
```

ユーザーファイルはコピーも送信もしない。既定値は600秒相当、OPMトラック0・MIDIトラック16、音階照合用の差+12。全ノートの順序照合・イベント内容ハッシュ一致・高精度側の変動が1観測ブロック以内であることを検証し、満たさなければエラーにする。600秒相当のOPM描画はこのMacで約4.34秒だった。

## 今回のブラウザー検証との区別

`scripts/verify-mdr-frame-sync.mjs` は、各イベントの送信予定時刻を、独立に記録したOPM出力フレームの予定時刻と比較する。UIの「同期差0 ms」は使用しない。この測定は予約方式の段差・累積補正・送信遅延を検出できるが、変換された曲内イベント時刻そのものの正しさや、SoundFontの実発音タイミングまで保証するものではない。
